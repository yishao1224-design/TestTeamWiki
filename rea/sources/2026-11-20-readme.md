## Product statement (lines 6-10, 61-67)

> # REA: Reverse Engineer Anything
>
> ### One MCP for reverse engineering across binaries, applications, and runtime behavior.
>
> **See a feature you like. Understand how it works, down to the binary level.**
>
> See a feature in an app that you want in your own product? Ask your agent to
> investigate it with REA. It can inspect the app without its source code,
> explain how the feature works, show the evidence, and build a version for
> your project.
>
> REA connects your agent to tools for inspecting native binaries, JavaScript
> and Electron apps, .NET assemblies, and websites. You can also use the same
> tools from your terminal. Analysis runs locally, and results include the
> evidence and limitations behind each conclusion.
>
> Setup registers REA with your agent and installs matching workflow
> instructions. Native analysis can use an existing Hopper, Ghidra, or IDA
> installation; setup can optionally install Hopper with approval. Static
> JavaScript analysis needs no native analysis engine.

## Quick start (lines 69-124, abridged)

> ```bash
> npx rea-agents setup
> ```
>
> Choose your agents, review the proposed changes, and approve them. Setup adds
> REA's MCP server and matching workflow instructions, with backups of existing
> configuration. Restart your agent afterward.
>
> Setup supports Claude Code, Codex, Cursor, Gemini CLI, Grok Build and
> [other agents](docs/installation.md#supported-agents).
>
> MCP uses compact input schemas by default to reduce context overhead. Set
> `REA_MCP_INPUT_SCHEMA_PROFILE=full` in your MCP registration when you need the
> complete advertised field guidance and nested validation details.
>
> ```bash
> npx -y rea-agents@latest analyze-javascript-application /absolute/path/to/app --json
> ```
>
> To install the `rea` command for regular use:
>
> ```bash
> npm install --global rea-agents
> rea --help
> ```
>
> ### Update REA
>
> ```bash
> rea update
> ```
>
> `rea --update` is an alias for this verified workflow and accepts the same global
> output flags.

## How REA works (lines 165-174)

> Your agent calls REA through MCP to inspect the target and trace relevant code.
> REA returns findings with their evidence. The agent uses them to ask follow-up
> questions, explain the behavior, or write and test an implementation.
> CLI commands use the same workflows.

| Target | What REA returns | Requirements |
| --- | --- | --- |
| Desktop installations | Runtime candidates, supporting files, component markers and next probes | Built-in bounded directory/header inspection |
| Native binaries | Pseudocode, assembly, strings, symbols, calls and references | Hopper, Ghidra or IDA |
| Offline ELF layout | Sections, segments, original symbols/relocations and static mitigation candidates | Caller-supplied pwntools on Linux x64 |
| Go binaries | Embedded compiler version, modules, replacements and build settings | Built-in static ELF/PE/thin Mach-O inspection |
| GPU code objects | CUDA/HIP targets, selected kernel parameters and resources, retained PTX text | Built-in static inspection |
| Model artifacts | GGUF / safetensors metadata, tensor declarations and derived totals | Built-in header inspection; optional full-file hash |
| IL2CPP metadata | Unity `global-metadata.dat` assembly images, type and method names and index ranges | Built-in static decoding of versions 24, 27, 29, 31 and 39 |
| Godot PCK | Archive inventory and extraction, original header/directory facts | Built-in static formats 2, 3 and 4 |
| Rust binaries | Embedded cargo-auditable crate names, versions, sources and dependency edges | Built-in static ELF/PE/thin Mach-O inspection |
| PE certificates | Authenticode WIN_CERTIFICATE entries and PKCS#7 signer/X.509 identity fields | Built-in static PE inspection |
| ELF notes | PT_NOTE/SHT_NOTE owners, types, GNU build-id and ABI-tag fields | Built-in static ELF inspection |
| Erlang BEAM | IFF chunks, atoms, exports, imports, lambdas and the Code header | Built-in static BEAM inspection |
| WASM artifact | Validation, sections, exact import/export WAT forms and decoded WAT | Caller-supplied WABT 1.0.42 |
| EVM bytecode | Dispatch selectors, byte offsets, inferred arguments and mutability | Local raw/hex carrier on Linux x64 |
| SQLite databases | Tables, columns, indexes, views, triggers and selected ordinary-table rows | Local database/WAL snapshot; Node.js 24.x >=24.15 or 26+ |
| Recorded Linux crashes | Raw notes, every recorded thread's registers/signals and optional mapping candidates | Caller-supplied pwntools on Linux x64 |
| JavaScript / Electron | Modules, imports, source maps, routes, IPC and native add-on relationships | Node.js and npm; Linux: procps-compatible `ps` |
| Websites | Page structure, scripts, network observations and requested screenshots | A Chrome-family browser |
| Saved network captures | Requests, responses, exposed payloads and source locations | HAR or Fiddler Everywhere SAZ |
| .NET assemblies | Metadata, CIL instructions, declared native dependencies and build comparisons | None (static only) |
| Android APKs | Manifest declarations, classes, decompiled methods and references | Headless JADX and a full JDK |
| APK signatures | v1/v2/v3/v3.1 signers, certificate fingerprints, key rotation | None (static only) |
| Android devices | Devices, packages, processes, logs, dumps, screen captures | Caller-supplied adb |
| JEB projects | Engine-backed project units, artifact digests and pseudo-code | A caller-started JEB client serving MCP (`REA_JEB_MCP_URL`) |
| Android resources | Decoded manifest, string tables, locales and version facts | Caller-supplied Apktool launcher |
| Flutter apps | Dart snapshot hash, per-ABI library digests and engine build provenance | None (static APK parsing) |
| Firmware | Regions, extraction results and native-analysis handoffs | Binwalk / Unblob on Linux |
| Recorded packets | Selected fields, repeated values, filters and decode-as rules | Linux: TShark 4.x + prlimit |
| Packet summaries | Endpoints, DNS, TLS SNI, protocol distribution and HTTP requests | Caller-supplied tshark and capinfos |

| Packages and resources | File inventories, digests, plists, Apple bundle anatomy | Built-in artifact readers |
| Process behavior | Terminal output, interactions, exit and filesystem observations | Linux/macOS with a native PTY |
| PyInstaller executables | CArchive members, Python version, entry scripts and extracted bytecode | None (static only) |

## Offline native providers (lines 223-240, abridged)

> For offline native-binary inspection, REA also supports caller-supplied GNU
> objdump and Rizin. REA does not install or update either provider.
>
> For large binaries, raise the provider's startup deadline with
> `REA_GHIDRA_STARTUP_TIMEOUT_MS` or `REA_HOPPER_STARTUP_TIMEOUT_MS`.

## FAQ claims (lines 279-331, abridged)

> Any agent that supports local MCP servers.
>
> Deep native analysis uses one of Hopper, Ghidra or IDA. Static JavaScript and
> .NET inspection work without a native analysis engine.
>
> REA starts Hopper when an operation needs it.
>
> Native analysis returns pseudocode and assembly. JavaScript/Electron analysis
> recovers modules and their relationships.
>
> REA analyzes targets locally. Your agent receives the tool results, and its
> model provider has its own data policy.
